# Retained answer authority

## Picking up a standalone Implement answer

When an Implement question is asked in the terminal, the person can answer in the agent's chat or choose **Answer here instead** in the App. For an App answer, use `qualitylayer question poll --task <task> --json` and match the question ID in `answered_meanwhile`. Poll picks up all unread answers for that task once. Use the saved answer without asking for it again.

The terminal ask and re-ask replies name this move. A closed `question answered` refusal points to the same command when the answer came through the App. Record new human words given in the agent's chat with `question answered --id <question-id>`. A saved App answer keeps the authority of the person's original choice.

## Bounded native session proof

Plain and compressed Codex histories use the same proof window: at most 1 MiB of identity/header bytes and 7 MiB of recent bytes once the history exceeds 8 MiB. Incomplete boundary rows are discarded; omitted middle records cannot establish a missing picker call or approval. Session, checkout, call, answer and completion checks retain their existing authority. Compressed histories are read as a stream while retaining only those windows, without materializing the whole decompressed history.

## Idle planning answer delivery

The last answer to a genuine App batch may continue only its original running, idle native planner at the existing accepted lead Stop. The Stop keeps its actual sequence and time through trailing SubagentStop and known idle_prompt notifications. Those informational records neither become a new Stop nor move its boundary. Unknown notifications, permissions, new work or prompts, real terminal input, interruption, explicit Stop/Pause, changed native session or generation and active workers still prevent delivery. A terminal focus report is protocol traffic, not the person's input or a reason to cancel a guarded handoff.

Saving, sending and consuming answers remain separate facts. The existing batch continuation records one attempt for that answer revision; native pickup alone marks consumption. No timer, retry, synthetic native event, approval or model instruction supplies missing evidence. Question continuation does not approve the Plan or the finished change.

This nonvisual contract covers the local-first answer-store migration. It does not activate the migration or apply a workflow-stage mapping. The two human approvals, revision checks, amendments, evidence, native questions and permissions keep their existing owners. Existing stage values remain original record data. The separately approved three-step workflow amendment belongs to its model and implementation owner; this storage layer never translates stages or infers an approval from that translation.

Item answers belong to the task's private runtime owner. Preserve each original id, order, kind, note, quote, exact item digest, delivery/pickup/reply state, withdrawal and native question receipt. Question history remains in `question.json`, `questions.json` and the question batches. Gates, decided snapshots, attestations and approved revisions remain authoritative in their current stores; conversion never writes a stage or creates an approval.

Legacy records are classified by their accepted shape and independently recorded binding. A known answer kind with an item is retained as answer history, including a materialized genuine answer carrying historical author metadata. Raw team/link mirrors, ordinary annotations and the word “approve” carry no approval authority. An unknown or stale binding stays historical: conversion must not stamp the current item digest onto it. Existing native receipt identity can establish the exact historical question/gate relationship, but cannot approve another revision.

Only an answer bound to the exact current item digest is eligible for new item pickup. A matching independently supplied native receipt includes the question id, number, picked label, receipt identity, item, document and accepted answer kind. When that exact question/gate revision independently preserved the item digest, the binding may retain that digest separately while leaving the original answer's absent `seen` untouched. An unbound receipt cannot supply today's digest. Answered, resolved or recipient-confirmed records are not offered again. Withdrawal/revisit remains a correction, and a change request never becomes agreement or approval. The existing question/gate stores continue to determine their own delivery and decisions.

Item pickup belongs to the existing native session's delivery cursor. The store reserves the existing `item:<id>:<created>` identity for that session and can return the same identified handoff after a committed-write error or process restart. Reservation leaves the answer's delivery/pickup evidence unchanged. A retry is suppressed and delivery recorded only when that recipient's existing cursor/native receipt confirms consumption; a missing native pickup timestamp is not invented. A saved reservation is not proof that stdout or native transport reached the recipient. Callers must preserve that distinction; physical exactly-once response delivery cannot be promised across a process loss. Already delivered history without a pending reservation remains history. No agent acknowledgment command or new workflow loop is introduced.

The converter accepts only an explicitly prepared incomplete migration for one registered owner, after legacy writers are quiescent. Its owner-bound native lock serializes current converters; source/asset rechecks refuse completion if an old writer changed the snapshot. It snapshots both local comment stores and referenced safe attachments, writes the retained answers and private archive, verifies them, then records completion. Failure keeps originals and leaves the conversion incomplete. Retry reuses exact ids and source hashes; concurrent pickup is serialized. No helper, polling loop, agent start, network request or new approval flow is introduced.

The first storage unit has no production callers. Activation requires one coordinated change to retained gate/question/batch/wait/item/page consumers and retirement of the mixed-store annotation writers. Two writable authorities are not an acceptable intermediate product state. Windows current-format record I/O fails closed as unsupported; Windows migration must remain inactive until its no-reparse native boundary is implemented and qualified. This is unfinished platform work, not a completed Windows migration.

## A2 integration contract (source preparation; activation pending)

Retained item writers, native question/batch pickup, point agreements, gate change detection, item/page projections and the existing wait cursor move together to the dedicated answer owner. The actual question, batch, gate, decided, attestation and amendment records retain their owners and identities. The upgrade adapter derives bindings from those real records and displayed revision, not caller JSON, an author label or current words substituted for an old unbound answer.

A formal Request changes action keeps its words on the gate/native decision record with the gate identity and revision. It is a changes decision even when its text says “approve”. Ordinary annotations stay inert in the private archive. Missing historical note provenance is not invented; exact native question/decision receipts may recover genuine context. No annotation pickup/resolve obligation or replacement helper is introduced.

Preparing a CLI response, a pre-emit save and the old wait cursor are not independent consumption proof. The existing native delivery owner supplies actual consumption evidence where supported. Otherwise the same stable identified item handoff remains recoverable with delivery unknown, without an agent acknowledgment command or synthetic transcript message. A fresh question/correction cannot be suppressed by an older item's receipt.

Old comment/thread/helper/CLI admissions and background writers must be quiescent before current-format activation. Original stores and bytes remain intact. A2 source may be prepared and tested with explicit synthetic migration state; it must not automatically upgrade production callers before independent R3 recheck plus quiescence and consumption qualification. Windows activation remains blocked.

Record I/O uses the trusted context filesystem port. The real context binds it lazily to the existing anchored native owner boundary; missing/unsupported capability fails safely. The virtual filesystem adapter exists only in test fixtures and is neither native qualification nor a licensing replacement. No environment setting or request body can select a port.

Runtime-only history references resolve through the port's fixed 64 KiB project-registration reader and sealed home, then validate the exact task runtime and registered live checkout. They do not fabricate a Task root or use arbitrary pathname access. Legacy canonical decided/question/gate history remains readable before current-format activation; unsupported current-format I/O is never caught and replaced by pathname access.

The current answer projection carries its independently bound digest explicitly. A later item revision cannot inherit an old chat agreement merely because the old record was delivered. Superseded drafts remain historical records; a withdrawal after a reserved or delivered handoff remains a new revisit correction. New attachment bytes belong to the dedicated answer record owner and its bounded attachment manifest. Migrated attachments refer to the immutable annotation archive entry. Both transports expose opaque record/answer/asset references with available/missing/unsafe state; legacy absolute paths remain only inside inert original evidence.

Current-format App mutations carry one stable action identity per person's action, reused for its transport retries. It identifies the saved record and never proves approval or native consumption. A retry of an earlier action after a later withdrawal returns its historical result without reactivating authority. Even an unsent withdrawal retains an inert action record so its own later retry cannot withdraw a newer answer. Answer and word-agreement updates share the existing answer transaction; retry reconciles an incomplete word update only while that action remains current. Current-format activation requires the matching App request transport.
