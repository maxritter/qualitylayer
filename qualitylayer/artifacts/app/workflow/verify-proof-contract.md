# Verify proof projection

Verify's generated stages and acceptance description read the existing recorded proof. A normal project-check receipt reused after the producer verifies the same current inputs counts as a successful check; reuse is not an unrun, stale or failed command. The fix summary retains the required-command, candidate, time and recorded-success checks. An unanswered finding or incomplete, failed, stale or mismatched proof never becomes a checked fix. The plural is “fixes”. This changes no check, verdict or approval authority.

A scoped recheck may carry an earlier acceptance pass only through the existing authorized carried set: unchanged step text, a standing verdict and retained evidence. The final acceptance rows keep those original evidence links and their recorded run and mode. A carried pass is not a new execution in the latest run. Missing provenance stays unknown; a missing file or invalidated carry is not replaced by an arbitrary older pass. The generated acceptance description and its evidence viewer read the same standing proof, while the original verdicts and failed histories remain unchanged.

The existing Verify lanes, sections and layout stay. No acknowledgment, new lookup command, extra review round or duplicate execution is required to make the projection complete.

## Section navigation

Choosing a section from On this page scrolls to and focuses its heading. Done means uses the same section anchor with or without a run-type mark. The next Tab continues from that heading to the next control. Pointer and keyboard selection share this behavior.

## Fix rounds and rechecks

Agents choose the next move within the approved scope. They can continue fixing and rechecking while the evidence supports meaningful progress. If the result is unchanged, they investigate or change approach before another recheck. A real blocker that requires the person uses the existing question path. Historical cap questions already asked or answered keep their authority, and the final review still needs the person's approval.

A recheck names each outstanding service need by its card and recorded state. The judge pairs a matching open need with the previous blocker evidence. Reported restoration calls for a bounded availability check. Other steps retain their own verdicts and evidence. A genuine regression case fails before the fix, passes after it and stays in the suite for later rounds.

## Task attribution and branch context

The task's walkthrough and fix facts use the existing positive ownership records. Its scoped file inventory also bounds the outside-card and dependency facts. A commit made after feedback is a fix only when this task's recorded commit set contains it; a date, branch range, Plan path or note cannot supply ownership. Mixed-file parts and pending or unavailable proof retain their existing meaning. Pending attribution cannot support “As planned” merely because no attributed deviation remains; positively known facts still show, and the existing pending details stay available.

Shipping a shared branch still discloses its complete source change separately from those task facts. A task-only summary cannot stand in for what the push or merge carries. The two approvals, current-head and revision checks, landing authority and source records keep their owners. This adds no bookkeeping or permission.

The generated “Changed from the Plan” section excludes routine manifests and lock files covered by the task cards. Their dependency facts and source diffs remain intact; an outside-card dependency or recorded amendment stays visible. A complete, unchanged scope reads “As planned.” Incomplete attribution retains its existing pending treatment.
