Workflow in three steps

Purpose
How a QualityLayer task runs. You plan and you verify; agents do everything between. Each step page shows what the App draws for a real task, the step's two files and who writes what.
Drawn from
The App's own parts (its diagram view, preview cards and task cards) and the files of two real tasks. Where a page makes something up, its Assumed line says so.

Three steps

PlanImplementVerify
  1. Plan The agent prepares it, you answer and approve

    The agent reads the code, asks what only you can answer and writes one Plan. You approve it once, before any code. Its Pull request action opens GitHub's compare page.

  2. Implement Agents

    The agents cut the Plan into slices and task cards and build them test first, without a stop. The board shows progress at a glance.

  3. Verify Agents check it, then you review and ship

    Agents that did not write the code check every Done means point and the diff, and the build session fixes what fails. Then the same page is your review and the pull request.

Who does what

  • You come in twice. On the Plan you answer the agent's questions and approve what will be built. On Verify you look at the code, the screens and each Done means point as it ran, then approve and ship.
  • Agents do the rest. They read the code, write the Plan, cut it into cards, build, check and fix. A question that only you can answer comes once, and the build runs on while it waits.
  • Three hard limits. Your two approvals, honest evidence (a pass needs a recorded check or verdict), and visible amendments to the approved Plan. Everything else is guidance the agent may adapt, saying why in the record.

A task's files

Each step has one file for people and one for agents. Each fact is written once, in one section of one file; QualityLayer copies nothing between them. Files shows where each kind of fact lives.

A bug

A bug runs the same three steps. Its Plan says what breaks and why, with the reproduction, and its Done means start with a real red before the fix. Implement's cards carry Reproduce and Fix; Verify shows each step before the fix and after it. See Bug fix.

Inside: few words, few reads

What keeps a task fast and cheap where you don't look, and keeps agents from getting stuck.

  • Two hand-overs. The approved Plan goes to the build, the build goes to the checks. Each later reader carries the people's Plan, its Constraints and the task cards.
  • One brief per step, served once per session. Every workflow verb (task start, build start, build done, verify, brief) serves a step's text once per session; repeats point at its saved brief file. build done hands over Verify's first move directly, and next only reads state and open moves.
  • Reading by size. No helper for a small task, one or two otherwise. Their reports stay short and are linked one line each, never pasted into a second file.
  • Only the Plan is amended. A task card that needs another file is just edited; plan amend records a visible change to what you approved.
  • A judgement fails only on a Done means point, a critical or high security finding, or lost data. A recheck judges only what failed and the lines the fix changed (without re-running whole-diff test authorship). qualitylayer verdict finish writes and validates the canonical iteration block from recorded verdicts.
  • Explicit review choices. Task-local Extra planners are separate paid planning runs, not a global Plan-review panel setting. Independent review, Design review and the optional second opinion retain their own configured models; generated-file handling follows the current review contract.
What the checks keep: the two approvals, a fresh judge that never wrote the code and rules on every Done means point, the project's checks and security scans, a security review when a trust boundary is crossed, and questions for decisions only the person can make.

Earlier tasks

Until 11 Nov 2026 a task ran seven steps: Discuss, Research, Plan, Outline, Implement, Verify and Review. Those tasks cannot be continued, approved or reopened.

  • They open as files. An earlier task stays in the task list with the mark earlier workflow and opens its Markdown files as plain files in the Files view. It has no step page.
  • Nothing converts them. Their folders and records stay on disk untouched. One check of the identity file (01-plan.md with layout: three) tells a task of this workflow from an earlier one.

One current workflow

This is the current Plan, Implement and Verify model. The retained app-13-1, ui-13-1 and Plan-on-GitHub draft material has one destination here: concise documents, acceptance as it actually ran, and revision-bound approvals. Earlier seven-step examples remain history, never a second current workflow.

  • GitHub is the retained external review destination. The Plan's Pull request contract keeps its people-facing Markdown order, Mermaid and screens, exact revision and comments returning to the planner. It does not restore GitLab, Confluence, Notion or a manual external-approval claim.
  • Plans stay concise. The small-task example keeps the behavior, approach and proof without a word quota or extra task mode. Machine Setup and cross-agent continuation stay in the App Model's after-v14 contract.
  • Implementation and evidence remain separate. The step pages and their people/agent files keep their schema and writer contracts. Model captures, draft adoption and source hashes never substitute for the actual acceptance run, the independent verdict or either human approval.
